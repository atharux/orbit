Plate 00

What Cypher even is

SQL describes tables and asks you to imagine the joins. Cypher does the opposite: you draw the shape you're looking for, in the query itself, using ASCII art. Parentheses are nodes. Square brackets are relationships. Arrows show direction. That's most of the syntax. 

MATCH (c:Contact)-[:WORKS_AT]->(v:Venue)
RETURN c.name, v.name

Read it as a sentence: "a Contact, that WORKS_AT a Venue."

That's the whole mental model. Every query you'll write is a variation on: draw the pattern you want, optionally narrow it with WHERE, then say what to RETURN — or, for writes, what to MERGE. There's no separate "join" keyword because the pattern is the join.

try it Every code block in this session is a real, runnable query against your schema. Open your app → Graph → click a node → Open in Neo4j Browser ↗ in the schema panel, and paste as you go.
Plate 01

Nodes, labels, properties

MATCH · RETURN · LIMIT

(v:Venue) means: bind a variable named v, to any node carrying the label Venue. The label is the node's kind. Properties live in { } when you're matching by them, or after a dot when you're reading them. 

MATCH (v:Venue)
RETURN v.name, v.district
LIMIT 5

This is the read side of exactly what your importer writes:

MERGE (v:Venue {venue_id: r.venueId})
  SET v.name = r.name, v.district = r.district, v.vertical_id = r.verticalId

syncToNeo4j.ts, Q_VENUES — the node this plate's MATCH is reading back.

exercise

Return the name of every Trades venue that has no website on file.

show query 
MATCH (v:Venue)
WHERE v.category = 'Trades' AND (v.website IS NULL OR v.website = '')
RETURN v.name
Plate 02

Relationships and patterns

-[:REL]→ · direction · multi-hop

A relationship pattern chains nodes together. Direction is real and matters — Orbit's WORKS_AT always points Contact → Venue, never the other way. Get the arrow backwards and you'll get an empty result, not an error, which is the single most common first-week Cypher bug. 

MATCH (c:Contact)-[:VERIFIED_BY]->(s:Source {name: 'linkedin-import'})
RETURN c.name, c.title
LIMIT 10

Chain more than one hop by just continuing the pattern — this is a Contact, the Venue they work at, and the Sequence targeting that Venue, all in one line:

MATCH (c:Contact)-[:WORKS_AT]->(v:Venue)<-[:TARGETS]-(s:Sequence)
RETURN c.name, v.name, s.name

Two relationships, one pattern — no explicit join anywhere.

note Drop the arrowhead — -[:WORKS_AT]- with no > — to match the relationship in either direction. Useful when you don't remember (or don't care) which way it points.
exercise

List every Contact enrolled in a Sequence, with that sequence's status.

show query 
MATCH (c:Contact)-[:ENROLLED_IN]->(s:Sequence)
RETURN c.name, s.status
Plate 03

WHERE — filtering the pattern

toLower() · CONTAINS · NOT EXISTS

WHERE narrows a pattern the same way it would narrow a SQL row — the difference is it can filter on the shape of the graph, not just property values. Your importer uses this constantly for case-insensitive matching, since business names arrive with inconsistent capitalization: 

MATCH (v:Venue)
WHERE toLower(v.name) = toLower('blitz elektrotechnik')
RETURN v

The pattern-shape filter — one of the presets in your own Ask panel, "Companies with no verified contact" — reads:

MATCH (v:Venue)
WHERE NOT EXISTS {
  MATCH (c:Contact)-[:WORKS_AT]->(v) WHERE c.verified
}
RETURN v.name

"No verified contact" isn't a property on Venue — it's an absence in the graph's shape.

exercise

Find every Contact whose title contains the word "electric" (any case).

show query 
MATCH (c:Contact)
WHERE toLower(c.title) CONTAINS 'electric'
RETURN c.name, c.title
Plate 04

Aggregation

count() · collect() · grouping by omission

Cypher has no GROUP BY. Instead: any column you RETURN that isn't wrapped in an aggregate function automatically becomes the group key. This trips up everyone coming from SQL exactly once, and then never again. 

MATCH (v:Venue)
RETURN v.district, count(v) AS n
ORDER BY n DESC

"Venue count by district" — v.district isn't aggregated, so it's the group.

collect() is count()'s sibling — instead of a number, gather the actual matches into a list:

MATCH (c:Contact)-[:VERIFIED_BY]->(s:Source)
RETURN s.name, collect(c.name) AS verifiedContacts
exercise

Which Venues have the most WORKS_AT contacts — "most-connected companies," ranked?

show query 
MATCH (c:Contact)-[:WORKS_AT]->(v:Venue)
RETURN v.name, count(c) AS contacts
ORDER BY contacts DESC
LIMIT 10
Plate 05

OPTIONAL MATCH

the graph's left join — and the trap inside it

Plain MATCH is an inner join: no match, no row. OPTIONAL MATCH keeps the row anyway, with every unmatched variable bound to null. This is exactly how your importer links a LinkedIn contact to an existing Venue without ever creating one: 

OPTIONAL MATCH (v:Venue)
  WHERE r.company IS NOT NULL
    AND toLower(v.name) = toLower(r.company)
    AND v.vertical_id = r.verticalId
FOREACH (_ IN CASE WHEN v IS NOT NULL THEN [1] ELSE [] END |
  MERGE (c)-[:WORKS_AT]->(v))

linkedinImport.ts, Q_IMPORT — OPTIONAL MATCH can't create a node, so this is structurally safe, not just careful.

the trap OPTIONAL MATCH can also return more than one row per input row — if two Venues happen to share a name, you get two output rows, and anything downstream (a MERGE, a count) silently runs twice. This is the exact bug class /code-review caught in this session's own diff, twice: once for Venue names, once for Contact+Venue name-fallback matching. The fix both times was the same — narrow the WHERE until only one match is possible, here by adding vertical_id to the condition.
exercise

Return every Venue, and the name of its Sequence if it has one — null if not.

show query 
MATCH (v:Venue)
OPTIONAL MATCH (s:Sequence)-[:TARGETS]->(v)
RETURN v.name, s.name
Plate 06

MERGE

writing that doesn't duplicate itself

CREATE always makes a new node — run the same import twice and you get two copies of everything. MERGE finds a node matching the given pattern, and only creates one if nothing matched. Your codebase's own comment says it best: 

// MERGE by stable keys so re-syncing the same lead is idempotent.
MERGE (c:Contact {contact_id: cid})
  SET c.name = r.name, c.title = r.title, c.vertical_id = r.verticalId
the footgun MERGE matches on every property inside the braces. Put two properties in the merge pattern — MERGE (v:Venue {name: x, district: y}) — and you've made the pair the identity, not name alone. That's usually not what you meant. Keep the merge pattern to a single stable key (an id), and set everything else afterward with SET — exactly the shape of every query in this codebase.
exercise

Write a MERGE that upserts a Source node by name, and stamps a last_seen property on every run.

show query 
MERGE (s:Source {name: 'linkedin-import'})
  SET s.last_seen = datetime()
Plate 07

WITH

chaining stages, and where your variables go to die

WITH is Cypher's pipe: it closes one stage of the query and opens the next. The critical rule — anything not named in the WITH clause is dropped. That's the entire explanation for "why did my variable disappear," which is the second most common beginner trap, right after the arrow direction from Plate 02.

Your import query is four stages long, and each WITH is a deliberate handoff:

UNWIND $rows AS r
OPTIONAL MATCH (existing:Contact)-[:WORKS_AT]->(v0:Venue) WHERE …
WITH r, coalesce(existing.contact_id, r.contactId) AS cid   // existing, v0 dropped here
MERGE (c:Contact {contact_id: cid}) SET …
WITH c, r                                                     // cid dropped here
OPTIONAL MATCH (v:Venue) WHERE …
FOREACH (… MERGE (c)-[:WORKS_AT]->(v))
WITH c, r, v                                                  // carried forward for Source linking
MERGE (src:Source {name: 'linkedin-import'}) SET …
MERGE (c)-[:VERIFIED_BY]->(src)

Every WITH is a name-your-carry-ons moment — only what's listed survives to the next stage.

rule of thumb When a variable you need "vanishes," it's almost never a bug in Cypher — it's a WITH upstream that didn't name it. Scroll up.
Plate 08

UNWIND

a parameter list becomes rows

Your driver code hands the query a JS array — one object per lead, per CSV row, per contact. UNWIND is what turns that single list parameter into one row per element, so the rest of the query can treat it exactly like a MATCHed row. 

UNWIND $rows AS r
MERGE (v:Venue {venue_id: r.venueId})
  SET v.name = r.name

The very first line of every write query you've shipped this session — this is how a 16-row CSV becomes 16 MERGEs in one round trip.

why it matters Without UNWIND, importing N rows means N separate queries — N network round trips to Aura. With it, one query call, one transaction, however many rows. That's the entire reason linkedinImport.ts builds a JS array first and hands it to Cypher as a single $rows parameter, instead of looping and calling tx.run() per contact.
Plate 09

FOREACH

Cypher's if-statement, for writes only

Cypher has no IF for side effects. The idiom is FOREACH over a list that's either empty or has one element — a zero-or-one-element list stands in for a boolean. Read this exactly once, slowly, and it stops being strange: 

FOREACH (_ IN
  CASE WHEN v IS NOT NULL THEN [1] ELSE [] END
  | MERGE (c)-[:WORKS_AT]->(v)
)
if v matchedCASE returns [1] — a one-element list — so FOREACH runs its body once.
if v didn't matchCASE returns [] — empty — so FOREACH runs its body zero times.
the _just a throwaway loop variable — the body never reads it, only the list's length matters.

Plain English: "if a Venue matched, link to it; otherwise, do nothing." That's the whole line.

Plate 10

Paths

shortestPath() — the native way

Your graph view's "find path between two selected nodes" runs client-side today — plain JS, breadth-first search over whatever's already loaded in the browser (findShortestPath in ask.ts). Cypher can do the same search natively, inside the database, which matters once the graph is too big to hold in memory on the client: 

MATCH p = shortestPath(
  (a:Venue {venue_id: $fromId})-[*..6]-(b:Venue {venue_id: $toId})
)
RETURN p

[*..6] means "any relationship type, up to 6 hops" — cap it, or a disconnected graph makes this search expensive.

worth knowing Not something to migrate today — the client-side version works fine at Orbit's current scale, and it means path queries don't need a round trip to Aura for something already on screen. File this under "the database-native way to do it," for the day the graph outgrows the browser tab.

Reading Q_IMPORT cold

Glossary, in the margin

the eleven words that cover almost everything you'll write

Label
a node's kind — :Venue, :Contact. A node can carry several; Orbit's never do.
Pattern
the ASCII drawing of nodes + relationships that a MATCH looks for.
MATCH
inner join — no match, no row.
OPTIONAL MATCH
left join — no match, row survives with nulls. Can also return >1 row per input.
WHERE
filters a pattern, by property or by shape (NOT EXISTS { … }).
RETURN
what the query hands back. Non-aggregated columns become the group key.
MERGE
find by the given pattern, create only if nothing matched. Idempotent by design.
SET
write properties onto an already-matched or -merged node.
WITH
closes a stage; only named variables carry forward.
UNWIND
list parameter → one row per element.
FOREACH
run a write 0 or 1 times, via a CASE … [1] … [] list trick.
